# Миграция 0007 — мультипродуктовая архитектура

Этапы 1 и 2 плана: модель доступа переехала с «есть/нет подписка» на
«продукты + доступы». Снаружи сайт должен работать точно как раньше.

## Порядок применения — строго такой

1. **Снять дамп базы.** Beget → phpMyAdmin → база `focuspkp_yoga` →
   Экспорт → метод «Обычный», формат SQL. Копию положить вне Beget.
2. **Применить SQL.** phpMyAdmin → вкладка SQL → вставить целиком
   содержимое `db/migrations/0007_products.sql` → выполнить.
3. **Прогнать сверку.** В том же файле внизу четыре закомментированных
   запроса. Раскомментировать и выполнить. Ожидаемый результат:
   - запрос 1: числа подписок и доступов совпадают;
   - запросы 2, 3, 4: пустой результат.
   Если запрос 2 или 3 вернул строки — **не деплоить код**, написать
   разработчику: значит, у кого-то доступ перенёсся неверно.
4. **Задеплоить код** — `git push` в `main`, GitHub Actions сам сделает
   rsync на Beget.
5. **Пройти чеклист проверки** (ниже).

### Если код уехал раньше SQL

Ничего страшного. Код сам определяет, применена ли миграция
(`access_model_ready()` в `includes/access.php`), и пока таблиц нет —
молча работает по старой таблице `subscriptions`. Участники доступ не
теряют. После применения SQL новая модель включится сама, без правок.

## Чеклист проверки после деплоя

- [ ] Действующий участник клуба видит уроки, дату окончания, избранное
- [ ] Участник на заморозке **не** потерял доступ
- [ ] Пробный пользователь видит только пробные уроки

- [ ] В админке: выдача доступа, заморозка, снятие заморозки, массовое продление
- [ ] В админке на дашборде появился блок «Активные доступы по продуктам»

## Откат

**Код:** `git revert` нужных коммитов и push. Тег последнего рабочего
состояния до этой работы — `pre-multiproduct-2026-11-24`.

**База:** откатывать не нужно. Миграция только добавляет таблицы и
таблицу `subscriptions` не трогает. Пока работает зеркалирование
(`legacy_sync_subscription()`), все выдачи доступа дублируются в
`subscriptions`, поэтому откат кода не теряет свежие оплаты.

Если всё же нужно убрать новые таблицы:

```sql
DROP TABLE IF EXISTS user_access;
DROP TABLE IF EXISTS orders;
DROP TABLE IF EXISTS product_topics;
DROP TABLE IF EXISTS products;
```

Порядок важен — из-за внешних ключей.

## Что изменилось в поведении

Намеренные отличия от того, как было (всё остальное — 1:1):

1. **Страница урока без доступа** больше не редиректит в кабинет, а
   показывает описание продукта и кнопку покупки.
2. **Пробный доступ теперь действительно ограничен** пробными уроками.
   Раньше замок был только визуальным в списке, и пробный пользователь
   мог открыть любой урок по прямой ссылке.
3. **Оплата заранее не съедает остаток срока.** Раньше оплата всегда
   отсчитывала 30 дней от сегодня; теперь продление считается от более
   поздней из двух дат — сегодня или текущее окончание.
4. **Повторный вебхук Prodamus не продлевает доступ дважды** — заказы
   с тем же `order_id` отбрасываются.
5. **Фильтр по статусу в списке пользователей заработал.** Он был
   заявлен в интерфейсе, но в запросе не применялся.
6. **Доступ действует до конца последнего дня.** В `user_access`
   дата окончания хранится как `23:59:59` этого дня.

## Что осталось неизменным намеренно

- Кнопка «нажми после оплаты» в профиле помечает заказ **оплаченным**,
  а такая же кнопка в кабинете — **ожидающим подтверждения**. Это
  расхождение было в коде и до миграции. От статуса зависит цена
  продления, поэтому поведение не меняли. Какой вариант правильный —
  решение Любови.
- Заморозка не отбирает доступ, а означает «админ продлит дату по
  заявке». Поэтому заморозка хранится флагом `is_frozen`, а не статусом.
